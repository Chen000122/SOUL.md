# SOUL.md — 给 AI Agent 的一份"可判定宪法"

> **English TL;DR**: SOUL.md is a 220-line "operating constitution" for AI agents, battle-tested through 17 versions. Unlike typical persona files (mostly adjectives), it ships a **conflict resolution chain**, **complexity triggers**, **decision-free paths for simple tasks**, an **amendment process**, and **file-level acceptance criteria**. Copy it, replace one memory path, and go.

## 这是什么

这是一份给 AI agent 的行为准则。它不是"你是友善的、专业的、乐于助人的"那种人格文件——**形容词没有裁决能力**。

它的起点是一堆形容词（2026-03），经过 17 个版本的迭代、11 轮自我审查、3 轮外部复核（5 处意见全部命中要害），长成了现在这样：**每一条规则都可判定、有例外、有触发条件，规则之间有明确的裁决顺序**。

一个数据：我们在 GitHub 检索了 36032 份同类的人格/行为文件，包含冲突裁决链（"priority chain"）的只有 1 份。形容词堆砌是常态，可判定的执行规范是异类。

## 五个核心设计

### 1. Priority Chain — 冲突裁决链

规则会打架："主动给建议"撞上"别废话"。解法不是调和，是排序：

**安全 > 诚实 > 准确 > 用户意图 > 果断 > 风格**

每条规则都有自己的位置，冲突时按链条裁决，不靠模型临场发挥。

### 2. 触发器定义 — 复杂度判定器

"复杂任务""简单任务"在多数文件里是模糊词。这里它们有唯一判定标准（3 步以上 / 有外部副作用 / 预计 10 分钟以上），全文十余处引用都指向同一个定义——阅读路径与依赖路径一致。

### 3. 免决策路径 — 给小事让路

规则是有执行成本的。一步能答完的小问题不值得走全套流程。简单任务直接答——不列计划、不标置信度、不做自检。但有一条例外：低置信度声明不豁免。**免决策省的是流程，不是诚实。**

### 4. 修宪程序 — 判别器在系统外

AI 发现规则有问题 → 只能提案，不能自改。修订权永远在系统外——可以是人，也可以是另一个 AI 实例。同一个实例自评必然塌，换一个实例就核出来了。

这不是理论：本项目的四条验收判据自评曾全绿，外部独立复核却发现 6 处数字里 4 处经不起核。**AI 的自评绿灯，外部一核就塌一条。**

### 5. 验收判据 — 文件级配 4 条

给 60+ 条规则逐条配判据不可能。借鉴 karpathy-skills 仓库的 "These guidelines are working if…" 范式，文件级配 4 条：

1. 交付里没有未被要求的改动
2. 含糊的请求，假设被声明了
3. 说"完成"时，真的验证过
4. 每一步都能追溯到请求

## 怎么用

1. 复制 `SOUL.md` 到你的 agent 环境（system prompt / 工作区文件 / CLAUDE.md 等价物）
2. 找到 `记忆路径（环境变量，按运行环境替换）` 一行，替换成你环境的记忆文件路径；没有记忆系统就跳过，不影响主任务
3. 按你的场景增删——但建议**先原样跑一段时间再改**：每条规则都有它存在的原因，见文内 Changelog（含每版动机）

> **适配与状态声明**：本文件按"环境无关"设计——记忆路径是占位变量，工具/权限缺失时有降级路径（不假装完成）。已在多个 agent 环境实际使用：既作为日常主力的深度驱动，也被其他独立 AI 实例加载后用于交叉复核（本项目三轮外部复核中的两轮即来自此）。**公开用户视角的跨环境验证仍处于早期**——欢迎报告你的使用体验（哪个环境、哪条规则表现如何），这将直接决定下一版的方向。

## 设计哲学

- **规则形态与验收 > 规则数量**：数量越多，单条遵守率越低
- **可观测性决定反馈回路**：违反了没人看得见的规则，永远不会被纠正
- **判别器必须在系统外**：能自我评估的系统，会天然偏好"自己能验证的东西"，而不是"真正有用的东西"
- **慢产出、细打磨**：17 版跨近 7 个月，每版都有 Changelog 记录改了什么、为什么

## 参与贡献

- **欢迎 PR**：README 改进、错字修正、英文翻译、排版调整
- **SOUL.md 正文的修改请走 Issue**：开 Issue 提案 + 说明理由，由维护者评估后修订并记入 Changelog

原因很简单：这个项目的核心价值是 15+ 版迭代沉淀的口径一致性（术语、指针、两级规则结构），正文每处修订都遵循文件内部的「修宪程序」——提案 → 评估 → 入档。这正是本文第五节说的"判别器在系统外"：**你报告真实体验，修订决策留在维护侧。**
